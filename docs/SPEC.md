# Course Specification — Data Analysis & Implementation

This is the contract every chapter of the course must satisfy. When this
document and a built chapter disagree, the chapter is the bug. Read
`docs/AUTHORING.md` for the mechanics of building a chapter.

The site is a sibling of *Programming for AI* and deliberately reuses its
architecture, navigation and visual language: a static, bilingual
(English/Arabic), offline-first PWA with one page per file and no network
request at run time.

### The audience, stated once

A student who has finished an introductory programming course (DSAI 1302 /
1303): variables, lists, dictionaries, loops, functions, basic pandas. They have
**not** taken statistics or machine learning. Two rules follow:

- **Every term of art is defined before it is used** — in the running text, in
  the student's own domain. A term used before it is defined is a defect.
- **Every derivation lives in an appendix**, not in the lesson body.

### The AI thread

The course is for a *Data Science and AI* major, so every lesson carries a
clear AI flavour, shown in an **AI lens** box: where this idea decides whether a
model trains well or silently fails (features and labels, data leakage,
encoding, training-ready tables, LLM/API JSON, unstructured text and images,
embeddings, drift, evaluation data). The flavour must be concrete, not
decorative.

## 1. Site

1. **PWA.** Installable, offline-capable, precaches every page and asset.
   The precache list is generated by `scripts/build-sw.py`.
2. **Light and dark themes**, both designed; follows the OS, then the reader's
   choice. Teal accent (distinct from the sibling course's blue).
3. **English and Arabic at full parity.** Every sentence, question, option,
   hint, explanation, solution, glossary entry, diagram label and UI string
   exists in both. Arabic sets `dir="rtl"`; code stays LTR. Arabic is *written*,
   not machine-translated, with the technical term followed by its English
   original where it helps (e.g. «المقياس الاسمي (Nominal)»).
4. **GitHub Pages**: served from the repository root. No build step on the
   server, no framework, no CDN, no web font, no analytics.
5. **Navigation.** Course home (both tracks) → chapter home → pages. Breadcrumbs,
   a side drawer with the whole chapter outline, an on-this-page jump list,
   previous/next paging in reading order, a reading-progress bar, back-to-top.
6. **Progress** (pages read, test scores, where you stopped) lives in
   `localStorage` only, namespaced `da.*` (the sibling course lives on the same
   origin and must not collide).
7. Natural, muted colours; no neon, no decorative gradients.

## 2. Material

1. **Basics to advanced inside every chapter.** Lessons start from what the
   student already knows and climb. Within a lesson, concepts are ordered
   simple → subtle → professional practice.
2. **A lot of practice.** Something to do every 5–10 minutes of reading: an
   inline check, an exercise with a hidden worked solution, or a step-through.
3. **Worked evolution of code (primary teaching device).** The main examples
   are written first the obvious way, then *improved version by version*
   (`evolve` component: Version 1 → 2 → 3, with the lines that changed marked
   and a sentence on what each change fixes and what it still leaves broken).
   These evolutions are **examined**: the tests include `compare`, `complete`,
   `error`, `write` and `contrast` questions about which version is better and
   why, not just recall.
4. **Problem threads across chapters.** The same kind of problem (loading a
   file, cleaning a column, answering "average rent per city") reappears in
   later chapters solved a better way. Each appearance carries a **Thread**
   box naming the earlier solution, the side effect or gap it had, and what the
   new tool closes — and warns what is still open. `docs/THREADS.md` is the
   register.
5. **Diagrams everywhere they help**: flowcharts, decision trees, sequence
   diagrams (e.g. API request/response), entity diagrams, mind-maps. Authored
   as Mermaid, pre-rendered to SVG at build time so they work offline and in
   both themes and both languages.
6. **Code execution widget.** Programs worth tracing get a step-through:
   Back/Next/Play/scrub; the current line highlighted; beside it a typed
   visualisation of what exists *now* — variables, array cells, dictionaries,
   DataFrame tables, trees, the call stack — with what just changed flagged,
   plus the output so far and a note on what is happening. Python traces are
   **generated by running the code in CPython** (`tools/trace_gen.py`), never
   hand-written or interpreted in JS. Spreadsheet/BI steps are hand-authored.
7. **Glossary per chapter**: every term of art used, with its meaning (both
   languages), a category, and *where it is used* (links to the headings).
8. **Every lesson ends with a test; every chapter ends with three tests.**

## 3. Tests

1. **Lesson test**: ≥ 20 questions (target 24), covering that lesson only.
2. **Chapter tests**: **three** per chapter — A (core), B (applied/code), C
   (advanced, cross-lesson) — all **the same size** (24 questions each) and
   together covering the whole chapter.
3. **Fourteen question types** (all must appear in every chapter):

   | Type | Key | Asks |
   |---|---|---|
   | True / false | `tf` | judge a claim |
   | Multiple choice | `mcq` | one correct option |
   | Choose all that apply | `multi` | several correct options |
   | Fill in the blank | `fill` | type the missing token(s) |
   | Put in order | `order` | sequence steps |
   | Order the code statements | `ordercode` | sequence code lines |
   | Match the pairs | `match` | pair two columns |
   | Find the error | `error` | click the offending line |
   | Complete the code | `complete` | pick/type the missing code |
   | Compare two versions | `compare` | judge version A vs B (code) |
   | Compare and contrast | `contrast` | place properties under concept A / B / both |
   | Write the output | `output` | type exactly what it prints |
   | Trace the value | `trace` | state a variable's value at a point |
   | Write the code | `write` | write code; checked for required parts |

4. **Every question carries**: difficulty (`easy|medium|hard`), topic tags that
   are **links to the course part to review**, a **hint** (hidden), an
   **explanation** (hidden until asked/answered) and the **answer** (hidden
   until asked). `complete`, `write`, `error`, `compare` also carry a worked
   solution.
5. **Full coverage**: every concept and every `evolve` step of the chapter is
   examined somewhere (the verifier checks every topic tag is used).

## 4. Quality bar

- **Every code output in a question or lesson is verified by running it** (CPython
  with the real pandas/NumPy). Not reasoned about.
- **Distractors are wrong for a reason the explanation names.**
- **Explanations teach**: why the tempting wrong answer is tempting; the rule to
  carry away.
- **Hints nudge, never give the answer away.**
- **The chapter argues honestly against itself**: name what each technique
  costs and when the simpler approach wins.
- **One consistent domain per chapter**; tests reuse the lesson's domain.
  Theory T1: rental listings + a school-registry API. Practical P1: a campus
  cafeteria's orders.
- Excel, Power BI and Jupyter instructions must be accurate for current
  versions (Microsoft 365 Excel; Power BI Desktop, Windows-only — with the free
  alternatives named); say plainly what a step needs (account, Windows, licence).

## 5. Non-negotiables

- No external network request at run time. No CDN, no web font, no analytics.
- Every page is committed, built. Works from `file://` (no service worker there).
- No framework, no bundler in the browser. Vanilla ES5 JavaScript.
- One page per file; a page loads only the CSS/JS/data it uses.
- No site content or source file identifies which AI model produced it.
- No data leaves the device; no account.
