Look at the raw file firstانظر إلى الملف الخام أولًا

Before any loader, read the first few lines yourself. The function below prints the first four lines of a file, cut at 76 characters so they fit. It uses only open and a loop. (The argument encoding="utf-8" matters: the adverts contain Arabic, and Windows would otherwise guess another encoding. Lesson 4 comes back to this.)

def peek(path, n=4):
    with open(path, encoding="utf-8") as f:
        for i, line in enumerate(f):
            if i == n:
                break
            print("   " + line.rstrip()[:76])

Concept 2 — Structured data: a table whose schema is promised in advanceالمفهوم 2 — البيانات المُهيكلة: جدول مخططه متفق عليه مسبقًا

The problemالمشكلة

You hold a handful of listings and two jobs: remove a listing whose owner took it down, and report the average rent per city. You reach for what you already know, one Python list per field. It works for a week.

بين يديك حفنة إعلانات ومهمتان: حذف إعلان سحبه صاحبه، وكتابة متوسط الإيجار لكل مدينة. فتمدّ يدك إلى ما تعرفه، قائمة بايثون لكل حقل. وينجح الأمر أسبوعًا.

Structured data is data in the shape of a table: every record is a row, every field is a column, every row has the same columns, and each column holds one kind of value. The schema (column names, types, rules) is fixed before the data arrives. A spreadsheet with a header row, a SQL table and our listings CSV are all structured; a CSV only lists the names, while a database also enforces the types.

البيانات المُهيكلة هي بيانات على هيئة جدول: كل سجل صف، وكل حقل عمود، ولكل صف الأعمدة نفسها، وكل عمود يحمل نوعًا واحدًا من القيم. والمخطط (أسماء الأعمدة والأنواع والقواعد) يُحدَّد قبل وصول البيانات. جدول البيانات الذي له صف عناوين وجدول SQL وملف الإعلانات CSV كلها مُهيكلة؛ لكن CSV لا يذكر إلا الأسماء، بينما تفرض قاعدة البيانات الأنواع أيضًا.

What it does. Three lists tied together only by position: item i of each list is supposed to describe listing i. Listing 1002 is withdrawn, and the function deletes from two lists and forgets the third. Nothing crashes, and nothing is right: 1003 is reported with rent 445 (its real rent is 590), 1004 with 590 (real: 315), and the Gaza list is [445] instead of [590]. Schema-on-write: the door that checksالمخطط عند الكتابة: بابٌ يفحص

A database takes the other road. You declare the schema first (columns, types, rules) and the database checks every new row at the door. That is schema-on-write. Think of airport security: the check happens at the gate, not in the air. Waiting in the queue is annoying, but the alternative is far worse. A rule worth memorising: reject early, suffer less later. Every faulty value you stop today is an hour of cleaning you never spend next year. Python ships with a small database engine, SQLite, so you can try it with nothing to install.

تسلك قاعدة البيانات الطريق المعاكس. تعلن المخطط أولًا (الأعمدة والأنواع والقواعد) وتفحص القاعدة كل صف جديد عند الباب. وهذا هو المخطط عند الكتابة (schema-on-write). تخيّل أمن المطار: التفتيش يجري عند البوابة لا في الجو. والانتظار في الطابور مزعج لكن البديل أسوأ بكثير. وقاعدة تستحق الحفظ: ارفض مبكرًا لتتعذب أقل لاحقًا. كل قيمة فاسدة توقفها اليوم هي ساعة تنظيف لن تقضيها بعد سنة. وتأتي بايثون بمحرك قاعدة بيانات صغير هو SQLite، فتجرّبه دون تثبيت أي شيء.

import sqlite3

con = sqlite3.connect(":memory:")
con.execute("""
    CREATE TABLE listings (
        listing_id   INTEGER PRIMARY KEY,
        city         TEXT NOT NULL,
        monthly_rent INTEGER CHECK (typeof(monthly_rent) = 'integer')
    )""")

con.execute("INSERT INTO listings VALUES (1001, 'Khan Younis', 415)")
print("1001 accepted")

try:
    con.execute("INSERT INTO listings VALUES (1002, 'Gaza', 'negotiable')")
except sqlite3.IntegrityError as err:
    print("1002 rejected:", err)

print(con.execute("SELECT COUNT(*) FROM listings").fetchone()[0], "row stored")

Honesty box — what structure costsصندوق الصراحة — ثمن الهيكلة

A fixed schema is rigid. If one landlord wants to add “has solar panels”, you must add a column that stays blank on most rows, or change the schema for everyone. When you have five records in a throwaway script, a list of dicts is perfectly fine: structure is worth its price when many records, many writers or many readers need to agree.

Honesty box — what flexibility costsصندوق الصراحة — ثمن المرونة

Self-description is not free. The keys are repeated in every record (file size), every reader must re-implement the checks that a database would do once (the survey, the .get rules), and two readers can disagree about what the schema is. Semi-structured data is the right choice when records genuinely differ, as with product pages that each carry different attributes, or when the producer changes faster than the consumers can be coordinated. When the records do not differ, a plain table with a few blank cells is simpler and safer.

الوصف الذاتي ليس مجانيًّا. فالمفاتيح تتكرر في كل سجل (حجم الملف)، وعلى كل قارئ أن يعيد كتابة الفحوص التي كانت قاعدة البيانات ستجريها مرة واحدة (المسح وقواعد .get)، ويستطيع قارئان أن يختلفا في تعريف المخطط. وتكون البيانات شبه المُهيكلة الخيار الصحيح حين تختلف السجلات فعلًا، كصفحات منتجات يحمل كل منها خصائص مختلفة، أو حين يتغيّر المُنتِج أسرع مما يمكن تنسيقه مع المستهلكين. وحين لا تختلف السجلات، فجدول عادي فيه بضع خانات فارغة أبسط وأسلم.

AI lensمنظور الذكاء الاصطناعي

Every web API, and every large language model you ask to “answer in JSON”, hands you semi-structured data. A model's reply can have the right keys, a wrong type ("three" instead of 3), a missing key, or a polite sentence wrapped around the JSON. All four happen in this tiny check, and only one of the four replies is usable:

كل واجهة برمجية على الويب، وكل نموذج لغوي كبير تطلب منه «أجب بصيغة JSON»، يسلّمك بيانات شبه مُهيكلة. وقد يحمل ردّ النموذج المفاتيح الصحيحة، أو نوعًا خاطئًا ("three" بدل 3)، أو مفتاحًا غائبًا، أو جملة مهذبة تلفّ الـ JSON. وكل الأربعة تحدث في هذا الفحص الصغير، ولا يصلح من الردود الأربعة إلا واحد:

import json

replies = [
    '{"rooms": 3, "area_m2": 95, "rent": 300}',
    '{"rooms": "three", "area_m2": 95, "rent": 300}',
    '{"rooms": 3, "rent": 300}',
    'Sure! Here is the JSON: {"rooms": 3}',
]

REQUIRED = {"rooms": int, "area_m2": (int, float), "rent": (int, float)}


def check(text):
    try:
        data = json.loads(text)
    except json.JSONDecodeError:
        return "not JSON"
    for key, kind in REQUIRED.items():
        if key not in data:
            return "missing " + key
        if not isinstance(data[key], kind):
            return key + " has the wrong type"
    return "ok"


for r in replies:
    print(f"{check(r):<25}<- {r}")

Concept 4 — Unstructured data: raw content with no fieldsالمفهوم 4 — البيانات غير المُهيكلة: محتوى خام بلا حقول

The problemالمشكلة

Look back at the listings table. Eight of its nine columns are structured. The ninth, advert, is a sentence typed by a landlord. Someone asks: “how many of our listings mention a balcony?” The table cannot answer, because the answer sits inside the text, in no column at all.

Treat that as a widely repeated rough estimate, not a measured fact: its source is rarely cited and it depends on what you count as “data”. The direction is not in doubt, though. For every table there are many more documents, e-mails, photographs and recordings, which is why so much of modern AI is aimed at them.

كثيرًا ما تقرأ أن نحو 80% من بيانات المؤسسات غير مُهيكلة. اعتبر ذلك تقديرًا تقريبيًّا متداولًا لا حقيقة مقيسة: فمصدره نادرًا ما يُذكر ويتوقف على ما تعدّه «بيانات». أما الاتجاه فلا شك فيه: فمقابل كل جدول توجد مستندات ورسائل بريد وصور وتسجيلات أكثر بكثير، ولهذا يتجه كثير من الذكاء الاصطناعي الحديث إليها.

A photograph is the clearest case. To a computer it is a grid of numbers, one per pixel; none of them is named “has a balcony”. The meaning lives in patterns across thousands of numbers.

Feature extraction: putting fields onto contentاستخراج السمات: وضع حقول على المحتوى

Feature extraction means writing rules (or training a model) that turn raw content into named, numeric fields: columns. It is the bridge from unstructured to structured. The simplest rules are string methods. Predict: how many of the 60 adverts contain the word “balcony”?

استخراج السمات (feature extraction، وتُسمّى أيضًا الخصائص) يعني كتابة قواعد (أو تدريب نموذج) تحوّل المحتوى الخام إلى حقول مسمّاة رقمية: أعمدة. وهو الجسر من غير المُهيكل إلى المُهيكل. وأبسط القواعد دوال النصوص. توقّع: كم إعلانًا من الستين يحوي كلمة «balcony»؟

import pandas as pd

df = pd.read_csv("rental_listings.csv")

df["has_balcony"] = df["advert"].str.contains("balcony", case=False, regex=False)
df["n_words"] = df["advert"].str.split().str.len()

print(df["has_balcony"].sum(), "of", len(df), "adverts mention a balcony")
print(df[["advert", "has_balcony", "n_words"]].drop_duplicates("advert").to_string(index=False))

Now the silent failure. A rule that looks right on the first example can be wrong on a whole group. Here is the “furnished” flag, first as a plain substring test, then as a whole-word pattern (\b marks a word boundary; the regex primer explains it). Predict both lists before running.

والآن الفشل الصامت. قاعدة تبدو صحيحة في المثال الأول قد تكون خاطئة في مجموعة كاملة. هذه علامة «مفروش»، أولًا باختبار جزء من النص، ثم بنمط كلمة كاملة (\b يرمز إلى حدّ كلمة؛ ويشرحه تمهيد التعابير النمطية). توقّع القائمتين قبل التشغيل.

import re

ads = [
    "Furnished flat in Gaza",
    "Unfurnished flat in Rafah",
    "Flat in Khan Younis, furnished kitchen only",
]

substring = ["furnished" in ad.lower() for ad in ads]
whole_word = [bool(re.search(r"\bfurnished\b", ad.lower())) for ad in ads]

print("substring :", substring)
print("whole word:", whole_word)
substring : [True, True, True] whole word: [True, False, True]

The substring test calls “Unfurnished flat in Rafah” furnished, because the word unfurnished contains the word furnished. The error is not random: it hits every unfurnished advert. The whole-word pattern fixes that, but look at the third advert, “furnished kitchen only”: it is still flagged True. Feature extraction is a judgement, and the honest way to hold it is: read a sample of matches by eye, and give the feature three states when needed (stated yes, stated no, not stated) instead of letting “not stated” become False.

يصف اختبار جزء النص «Unfurnished flat in Rafah» بأنه مفروش، لأن كلمة unfurnished تحوي كلمة furnished. والخطأ ليس عشوائيًّا: فهو يصيب كل إعلان غير مفروش. ويصلح نمط الكلمة الكاملة هذا، لكن انظر إلى الإعلان الثالث «furnished kitchen only»: ما زال يُعلَّم True. فاستخراج السمات حكم وتقدير، والطريقة الأمينة في التعامل معه: اقرأ عينة من المطابقات بعينك، وأعطِ السمة ثلاث حالات عند الحاجة (مذكور بنعم، مذكور بلا، غير مذكور) بدل أن يصير «غير مذكور» هو False.

The test "furnished" in ad.lower() returns True for “Unfurnished flat in Rafah”. What is the best repair?الاختبار "furnished" in ad.lower() يعيد True للإعلان «Unfurnished flat in Rafah». ما أفضل إصلاح؟

The first option. A substring test cannot tell furnished from unfurnished because the second word literally contains the first. A word-boundary pattern matches only the whole word. Changing the case (second option) changes nothing here, deleting adverts with “un” (third) would also delete “university” and “unit”, and the fourth option is the dangerous one: the error is not random, it hits every unfurnished advert, so the feature is systematically wrong. Even the repaired test misreads “furnished kitchen only”, so always read a sample of matches by eye.
الخيار الأول. اختبار الجزء من النص لا يميّز furnished من unfurnished لأن الكلمة الثانية تحتوي الأولى حرفيًّا. أما نمط حدود الكلمة فيطابق الكلمة كاملة فقط. تغيير حالة الأحرف (الخيار الثاني) لا يغيّر شيئًا هنا، وحذف الإعلانات التي فيها «un» (الثالث) سيحذف أيضًا «university» و«unit»، والخيار الرابع هو الخطر: فالخطأ ليس عشوائيًّا بل يصيب كل إعلان غير مفروش، فتصير السمة خاطئة بانتظام. وحتى الاختبار المصلَّح يسيء قراءة «furnished kitchen only»، فاقرأ دائمًا عينة من المطابقات بعينك.

Embeddings: letting a model choose the columnsالتضمينات: دع نموذجًا يختار الأعمدة

Hand-made rules have a ceiling. Here three adverts become rows of counts over a vocabulary we chose ourselves:

للقواعد اليدوية سقف. هنا تتحول ثلاثة إعلانات إلى صفوف عدّادات على مفردات اخترناها بأنفسنا:

ads = [
    "Sunny apartment, balcony, newly painted",
    "Bright flat with a terrace, newly painted",
    "Ground floor flat, close to the university",
]
vocab = ["balcony", "terrace", "university", "painted"]


def count_vector(text):
    words = text.lower().replace(",", "").split()
    return [words.count(w) for w in vocab]


print("columns:", vocab)
for ad in ads:
    print(count_vector(ad), "<-", ad)
columns: ['balcony', 'terrace', 'university', 'painted'] [1, 0, 0, 1] <- Sunny apartment, balcony, newly painted [0, 1, 0, 1] <- Bright flat with a terrace, newly painted [0, 0, 1, 0] <- Ground floor flat, close to the university

Each advert is now a list of four numbers, so a model could use it. But “balcony” and “terrace” are different columns, although a tenant would find the first two adverts alike; they share only the painted column. We would have to list every synonym by hand. An embedding is the learned answer: a model reads a piece of text and returns a list of numbers (commonly a few hundred to a few thousand, depending on the model) arranged so that texts of similar meaning get similar lists. You do not design the columns; the model learned them from very large amounts of text. Large language models work on such lists of numbers inside. This course needs only the idea, not the mathematics: text becomes a row of numbers, and similar meaning means nearby numbers.

صار كل إعلان قائمة من أربعة أرقام، فيمكن لنموذج أن يستعملها. لكن «balcony» و«terrace» عمودان مختلفان، مع أن المستأجر سيجد الإعلانين الأولين متشابهين؛ فهما لا يشتركان إلا في عمود painted. وسيكون علينا سرد كل مرادف يدويًّا. أما التضمين (embedding) فهو الجواب المتعلَّم: يقرأ نموذج قطعة نص ويعيد قائمة من الأرقام (عادةً من مئات قليلة إلى آلاف قليلة بحسب النموذج) مرتبة بحيث تحصل النصوص المتقاربة في المعنى على قوائم متقاربة. أنت لا تصمم الأعمدة؛ فقد تعلّمها النموذج من كميات ضخمة جدًّا من النصوص. وتعمل النماذج اللغوية الكبيرة على قوائم أرقام كهذه في داخلها. ويحتاج هذا المقرر الفكرة فقط لا الرياضيات: النص يصير صفًّا من الأرقام، والمعنى المتقارب يعني أرقامًا متقاربة.

Honesty box — what extraction costsصندوق الصراحة — ثمن الاستخراج

Every extraction loses information: has_balcony = True forgets that the advert said “large balcony overlooking the street”. Rules must be written, tested on a sample, and maintained when landlords start writing “terrace” or in Arabic. A language model can do the extraction for you, but it costs computing time and money, and its output still needs checking. For 60 adverts, reading them yourself in ten minutes beats any pipeline; extraction pays for itself when there are thousands and they keep arriving.

كل استخراج يفقد معلومات: فـ has_balcony = True ينسى أن الإعلان قال «شرفة كبيرة تطل على الشارع». والقواعد تحتاج أن تُكتب وتُختبر على عينة وتُصان حين يبدأ الملّاك بكتابة «terrace» أو بالعربية. ويستطيع نموذج لغوي أن يقوم بالاستخراج عنك، لكن بكلفة زمن حوسبة ومال، ويظل ناتجه بحاجة إلى فحص. ومع 60 إعلانًا تتفوق قراءتك لها بنفسك في عشر دقائق على أي خط معالجة؛ ويسدّد الاستخراج كلفته حين تكون الإعلانات بالآلاف وتتواصل بالوصول.

Much of the AI in the news reads unstructured data: language models read text, vision models read pixels. They too need numbers, so text is cut into pieces and mapped to vectors before any learning starts. The extraction step is where the information is decided: a feature you did not extract cannot be learned, and a feature you extracted wrongly is learned wrongly. A classifier trained on the substring-based furnished flag above would be taught, with full confidence, that unfurnished flats are furnished. Embeddings make the step less manual, not less important.

كثير من الذكاء الاصطناعي المتداول يقرأ بيانات غير مُهيكلة: النماذج اللغوية تقرأ النص ونماذج الرؤية تقرأ البكسلات. وهي أيضًا تحتاج أرقامًا، فيُقطَّع النص ويُحوَّل إلى متجهات قبل أن يبدأ أي تعلّم. وخطوة الاستخراج هي التي تُقرِّر المعلومات: سمة لم تستخرجها لا يمكن تعلّمها، وسمة استخرجتها خطأً تُتعلَّم خطأً. فمصنِّف يتدرّب على علامة furnished المبنية على اختبار الجزء من النص أعلاه سيُعلَّم، بثقة تامة، أن الشقق غير المفروشة مفروشة. والتضمينات تجعل الخطوة أقل يدوية لا أقل أهمية.

Colleagues use storage words as if everyone shared them: “put it in the warehouse”, “just dump it in the lake”, “it's in Mongo”. Each phrase quietly names a shape of data and a first step. If you do not have the whole comparison in your head, you will pick the wrong home for the data, and the wrong first move.

Where each shape lives, and when the schema is checkedأين يعيش كل شكل، ومتى يُفحص المخطط

A relational database stores structured tables and enforces their schema on write. A data warehouse is such a database built for analysis, holding cleaned tables gathered from many sources. A document store (the NoSQL databases of Concept 3) keeps semi-structured documents. And a data lake is cheap storage that keeps data in its raw form, whatever its shape: tables, JSON, photos and recordings side by side, loaded as they arrive and given structure later, when someone needs it. A lake is schema-on-read at the scale of a whole organisation. The diagram shows the two ways a store can treat a bad rent: reject it at the door, or accept everything and let the consumer deal with it.

تخزّن قاعدة البيانات العلائقية جداول مُهيكلة وتفرض مخططها عند الكتابة. ومستودع البيانات قاعدة كهذه مبنية للتحليل، تحوي جداول منظَّفة جُمعت من مصادر كثيرة. ومخزن المستندات (قواعد NoSQL في المفهوم 3) يحفظ مستندات شبه مُهيكلة. أما بحيرة البيانات (data lake) فتخزين رخيص يحفظ البيانات بصورتها الخام مهما كان شكلها: جداول وJSON وصور وتسجيلات جنبًا إلى جنب، تُحمَّل كما تصل وتُعطى بنية لاحقًا حين يحتاجها أحد. والبحيرة مخطط عند القراءة على مقياس مؤسسة كاملة. ويُري المخطط طريقتين يعامل بهما المخزن إيجارًا معيبًا: يرفضه عند الباب، أو يقبل كل شيء ويترك للمستهلك أن يتدبر الأمر.

These pairings are tendencies, not laws. PostgreSQL can store a JSON column, and a lake often holds Parquet files that are really tables. So ask the three questions of the data, not of the product name on the box.

هذه الاقترانات ميول لا قوانين. فبوسع PostgreSQL أن يخزّن عمود JSON، وكثيرًا ما تحوي البحيرة ملفات Parquet هي جداول في الحقيقة. فاطرح الأسئلة الثلاثة عن البيانات لا عن اسم المنتج المكتوب على العلبة.

Honesty box — pay once, or pay every timeصندوق الصراحة — ادفع مرة، أو ادفع كل مرة

Schema-on-write costs effort up front: you design the table, you write the constraints, you reject and fix incoming data. Schema-on-read costs nothing at the door and a little at every read, forever, by every reader. Neither is better in general. The first wins when many people read and the data must be trustworthy; the second wins when you do not yet know what you will ask, or when the data changes faster than any schema can follow.

المخطط عند الكتابة يكلّف جهدًا في البداية: تصمّم الجدول وتكتب القيود وترفض البيانات الواردة وتصلحها. والمخطط عند القراءة لا يكلّف شيئًا عند الباب ويكلّف قليلًا عند كل قراءة، إلى الأبد، على كل قارئ. وليس أحدهما أفضل مطلقًا. يفوز الأول حين يقرأ ناس كثيرون ويجب أن تكون البيانات موثوقة، ويفوز الثاني حين لا تعرف بعد ماذا ستسأل، أو حين تتغير البيانات أسرع مما يستطيع أي مخطط اللحاق به.

A spectrum, not three boxesطيف لا ثلاثة صناديق

Real datasets are usually hybrids. Our own listings CSV is eight structured columns plus one unstructured column. An e-mail has a semi-structured header (From, To, Date, Subject) and a free-text body. A scanned school form is mostly pixels with a little metadata (date, size, scanner). Do not force a box on such data; name the dominant shape and the parts that differ, and give each part its own first step.

معظم مجموعات البيانات الحقيقية هجينة. فملف الإعلانات CSV عندنا ثمانية أعمدة مُهيكلة وعمود واحد غير مُهيكل. ورسالة البريد لها ترويسة شبه مُهيكلة (From وTo وDate وSubject) وجسم نصي حر. واستمارة مدرسية ممسوحة ضوئيًّا بكسلات في معظمها مع قليل من البيانات الوصفية (التاريخ والحجم والماسح). لا تفرض صندوقًا على بيانات كهذه؛ سمِّ الشكل الغالب والأجزاء المختلفة، وأعطِ كل جزء خطوته الأولى الخاصة.

An e-mail has From, To, Date and Subject lines, a free-text body and a photo attachment. How should you describe its shape?رسالة بريد إلكتروني فيها From وTo وDate وSubject، ونص حر في الجسم، وصورة مرفقة. كيف تصف شكلها؟

The second option. Real datasets are usually hybrids, so the useful skill is to name the dominant shape and the parts that differ, then treat each part with its own step (read the header fields, extract features from the body, embed the photo). Calling it “structured” because of how a program displays it (first option) confuses the interface with the data. The third and fourth options each look at one part and ignore the others.
الخيار الثاني. معظم البيانات الحقيقية هجينة، فالمهارة النافعة هي تسمية الشكل الغالب والأجزاء المختلفة ثم معالجة كل جزء بخطوته: اقرأ حقول الترويسة، واستخرج سمات من الجسم، وأنشئ تضمينًا للصورة. أما وصفها بـ«مُهيكلة» بسبب طريقة عرض البرنامج لها (الخيار الأول) فخلط بين الواجهة والبيانات. والخياران الثالث والرابع ينظر كل منهما إلى جزء ويتجاهل الباقي.

The shape decides where the label comes from. In a structured table the label is often already a column (“was the flat rented within 30 days?”). For unstructured data the label has to be made: someone reads adverts and ticks “family-friendly” or not, and two readers will disagree on some. That disagreement is noise the model will learn faithfully, so label quality sets a ceiling on what any model can do. And since a lake keeps raw data while a model needs a table, keep the table derived and versioned (which files, which rules, which date), or you will not be able to rebuild next month the training set you used today.

The second option. The obstacle is not the file format or its speed; it is that a model computes with a fixed-size row of numbers, so every example must have the same columns, in the same order, all numeric. Turning a dict or a sentence into such a row is the real work, and it has to be done the same way for training data and for new data. The first option is false (models happily read files; what they cannot do is guess which keys are columns), and the third and fourth are plausible-sounding but beside the point.

The extraction code is part of the model. Whatever turns an advert into a row at training time must turn a new advert into a row at prediction time in exactly the same way: the same patterns, the same currency rule, the same column order.     lo, hi = LIMITS[key]
    return lo <= value <= hi

AI lensمنظور الذكاء الاصطناعي

Parsing quality is data quality. In Version 2's output the rent column held 300, 300 and 1200 on one scale although the 1200 was shekels; a model trained on it would learn a relationship between size and price that reflects a unit error, not the market. import json
import pandas as pd

with open("schools.json", encoding="utf-8") as f:
    schools = json.load(f)["results"]


def flat_school(s):
    contacts = s.get("contacts", {})
    return {
        "id": s["id"],
        "name": s["name"]["en"],
        "governorate": s["governorate"],
        "level": s["level"],
        "boys": s["enrolment"]["boys"],
        "girls": s["enrolment"]["girls"],
        "n_facilities": len(s["facilities"]),
        "phone": contacts.get("phone"),
        "email": contacts.get("email"),
    }


table = pd.DataFrame([flat_school(s) for s in schools])
print(table.shape)
print(table.isna().sum()[["phone", "email"]].to_dict())
