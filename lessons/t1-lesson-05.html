Concept 1 — JSON: nested text that Python already speaksالمفهوم 1 — JSON: نصّ متشعّب تتحدّثه بايثون أصلًا

The problemالمشكلة

Until now every file was a rectangle. The registry is not. A school has two names, an enrolment that is itself a pair of numbers, a location, a list of facilities and, for ten schools out of thirteen, a contacts object with a phone and sometimes an email. Squeeze that into a CSV and you must invent column names, decide what to do with the list, and pick a value for the three schools that have no contacts at all. A web service avoids the squeeze: it sends the structure as it is, as JSON.

كل ملف حتى الآن كان مستطيلًا. أما السجلّ فليس كذلك. للمدرسة اسمان، وأعداد طلبة هي نفسها زوج من الأرقام، وموقع، وقائمة مرافق، ولعشر مدارس من ثلاث عشرة كائن اتصال فيه هاتف وأحيانًا بريد. إن حشرتَ هذا في CSV فعليك أن تخترع أسماء أعمدة، وتقرّر ما تفعله بالقائمة، وتختار قيمة للمدارس الثلاث التي لا اتصال لها أصلًا. الخدمة على الويب تتجنّب هذا الحشر: ترسل البنية كما هي بصيغة جسون (JSON).

JSON (JavaScript Object Notation) is a plain-text format for nested data. An object { } holds named values, an array [ ] holds an ordered list, and a value is a string, a number, true, false, null, or another object or array. Strict on the way in (and one surprising exception)صارم عند الدخول (مع استثناء مفاجئ)

JSON is stricter than Python: strings use double quotes, no trailing comma, nothing before or after the document. A parser that sees anything else raises json.JSONDecodeError. Four inputs, four verdicts:

JSON أصرم من بايثون: النصوص بعلامات اقتباس مزدوجة، ولا فاصلة زائدة، ولا شيء قبل الوثيقة أو بعدها. وأي مُحلِّل يرى غير ذلك يرفع json.JSONDecodeError. أربعة مدخلات وأربعة أحكام:

import json

samples = {
    "single quotes":  "{'id': 7}",
    "trailing comma": '{"id": 7,}',
    "prose first":    'Here is the JSON: {"id": 7}',
    "NaN":            '{"ratio": NaN}',
}
for label, text in samples.items():
    try:
        print(f"{label:<15} parsed   {json.loads(text)}")
    except json.JSONDecodeError as err:
        print(f"{label:<15} rejected {err.msg} (char {err.pos})")
single quotes rejected Expecting property name enclosed in double quotes (char 1) trailing comma rejected Illegal trailing comma before end of object (char 8) prose first rejected Expecting value (char 0) NaN parsed {'ratio': nan}

The last line is the dangerous oneالسطر الأخير هو الخطِر

Python's parser accepts NaN, which the JSON standard does not allow, and json.dumps will happily write it. A file that Python reads without complaint can be rejected by another tool, and a nan that sneaks in is a number that is not a number. (On the writing side, json.dumps(..., allow_nan=False) makes Python strict too.) The message wording of the other three varies a little between Python versions; the verdicts do not.

مُحلِّل بايثون يقبل NaN مع أن معيار JSON لا يسمح بها، وتكتبها json.dumps بكل رحابة. ملف تقرؤه بايثون دون شكوى قد ترفضه أداة أخرى، وnan يتسلّل هو رقمٌ ليس برقم. (وعند الكتابة تجعل json.dumps(..., allow_nan=False) بايثون صارمة أيضًا.) صياغة رسائل الأسطر الثلاثة الأخرى تختلف قليلًا بين إصدارات بايثون؛ أما الأحكام فلا.

AI lensمنظور الذكاء الاصطناعي

A language model does not return JSON; it returns text that is often JSON. "Here is the JSON: {...}" fails exactly like the third line above, and a trailing comma — a classic slip — like the second. A pipeline that calls json.loads(reply) will crash on some fraction of replies, or, worse, wrap it in try/except: continue and silently drop those rows from your training set. Always count the failures. Concept 7 builds the checker.

النموذج اللغوي لا يعيد JSON؛ يعيد نصًّا هو في الغالب JSON. عبارة «هذا هو الـ JSON: {...}» تفشل تمامًا مثل السطر الثالث أعلاه، والفاصلة الزائدة — زلّة كلاسيكية — مثل السطر الثاني. وخطّ المعالجة الذي يستدعي json.loads(reply) سينهار عند نسبة من الردود، أو — وهو الأسوأ — يلفّها بـ try/except: continue فيُسقط تلك الصفوف من بيانات تدريبك بصمت. احسب الإخفاقات دائمًا. وسنبني المدقّق في المفهوم 7.

Writing JSON back: dumps, indent, ensure_ascii — and what a round trip changesكتابة JSON من جديد: dumps وindent وensure_ascii — وما يغيّره الذهاب والإياب

json.dumps(obj) returns text; json.dump(obj, f) writes to an open file. Two options matter every day. indent=2 lays the text out for human eyes. ensure_ascii is True by default, which escapes every non-ASCII character: valid, but an Arabic name becomes a row of مد…. Use ensure_ascii=False and open the file with encoding="utf-8".

تُعيد json.dumps(obj) نصًّا، وتكتب json.dump(obj, f) في ملف مفتوح. وخياران يهمّان كل يوم. الخيار indent=2 ينسّق النصّ لعين الإنسان. أما ensure_ascii فقيمته الافتراضية True وهي تحوّل كل حرف غير لاتيني إلى رمز هروب: صحيح لكنه يحوّل الاسم العربي إلى صفّ من مد…. استعمل ensure_ascii=False وافتح الملف بـ encoding="utf-8".

import json

name = {"ar": "مدرسة 1 (غزة)"}
print(json.dumps(name))
print(json.dumps(name, ensure_ascii=False))
print(json.dumps({"a": [1, 2], "b": {"c": None}}, indent=2))
{"ar": "\u0645\u062f\u0631\u0633\u0629 1 (\u063a\u0632\u0629)"} {"ar": "مدرسة 1 (غزة)"} { "a": [ 1, 2 ], "b": { "c": null } }

A round trip, loads(dumps(x)), is not an identity. JSON has no integer keys, no tuples and no NaN:

الذهاب والإياب، loads(dumps(x))، ليس مطابقة تامة. فـ JSON لا تعرف مفاتيح صحيحة ولا صفوفًا مرتّبة (tuple) ولا NaN:

import json

original = {1: "one", "pair": (3, 4), "ok": True}
back = json.loads(json.dumps(original))
print(back)
print(back == original)
print(json.dumps({"rent": float("nan")}))
{'1': 'one', 'pair': [3, 4], 'ok': True} False {"rent": NaN}

The integer key 1 came back as the string "1", the tuple as a list, and the comparison with the original is False — with no error anywhere. Treat JSON as a message format, not as a way to save Python objects.

عاد المفتاح الصحيح 1 نصًّا "1"، وعاد الـ tuple قائمة، وصارت المقارنة بالأصل False — دون أي خطأ في أي مكان. عامِل JSON على أنها صيغة رسائل، لا وسيلة لحفظ كائنات بايثون.

What does json.loads(json.dumps({2: (1, 2)})) return?ماذا تعيد json.loads(json.dumps({2: (1, 2)}))؟

JSON object keys are strings, so 2 becomes "2", and a tuple is written as an array and comes back as a list. The first option is the tempting one — it is what we wish for — but the round trip is lossy. TypeError is raised only for types JSON has no form for at all, such as a date.
مفاتيح كائنات JSON نصوص، فيصير 2 إلى "2"، ويُكتب الـ tuple مصفوفة ويعود قائمة. والخيار الأول هو المغري — فهو ما نتمنّاه — لكن الذهاب والإياب يفقد شيئًا. ولا يُرفع TypeError إلا للأنواع التي لا شكل لها في JSON أصلًا مثل date.

Reading nested data is giving an address: data["results"][0]["enrolment"]["boys"] means "the list under results, its first record, that record's enrolment, its boys". Every step is either a key (into an object) or a position (into an array). The next concept is about what happens when a step in the address does not exist.

قراءة البيانات المتشعّبة هي إعطاء عنوان: data["results"][0]["enrolment"]["boys"] تعني «القائمة تحت results، وسجلّها الأول، وenrolment لذلك السجلّ، وboys فيه». كل خطوة إما مفتاح (داخل كائن) وإما موضع (داخل مصفوفة). والمفهوم التالي يتناول ما يحدث حين لا توجد خطوة من خطوات العنوان.

XML in one paragraphXML في فقرة واحدة

XML is JSON's older, more verbose cousin: nested, labelled data written with opening and closing tags and attributes, still common in government statistics feeds, RSS, sitemaps and Office files. The idea is identical — a tree you walk with keys and positions — but everything is text, so boys comes back as '272', not 272, and you convert it yourself. Python reads it with the standard-library xml.etree.ElementTree (pandas has read_xml for simple record-shaped files). All of this lesson's habits — optional elements, flattening, pagination — carry over; only the parser changes. If you choose the format, choose JSON; if the source is XML, you do not need to fear it.

XML هي ابنة عمّ JSON الأقدم والأكثر إسهابًا: بيانات متشعّبة معنونة تُكتب بوسوم فتح وإغلاق وسمات، وما زالت شائعة في خلاصات الإحصاءات الحكومية وRSS وخرائط المواقع وملفات Office. الفكرة نفسها — شجرة تمشي عليها بالمفاتيح والمواضع — لكن كل شيء نصّ، فتعود boys على هيئة '272' لا 272 وتحوّلها بنفسك. تقرؤها بايثون بوحدة المكتبة القياسية xml.etree.ElementTree (ولدى pandas الدالة read_xml للملفات البسيطة ذات شكل السجلّات). وكل عادات هذا الدرس — العناصر الاختيارية والتسطيح والتصفيح — تنتقل كما هي؛ ولا يتغيّر إلا المُحلِّل. إن كان الاختيار لك فاختر JSON، وإن كان المصدر XML فلا داعي لأن تخافه.

import xml.etree.ElementTree as ET

xml_text = '<school id="203"><name lang="en">School 3 (Rafah)</name><enrolment boys="272" girls="183"/></school>'
root = ET.fromstring(xml_text)

print(root.tag, root.attrib)
print(root.find("name").text, root.find("enrolment").attrib)

Concept 2 — Reading nested data safelyالمفهوم 2 — قراءة البيانات المتشعّبة بأمان

The problemالمشكلة

The outreach team asks one question: how many schools can we email? The obvious code is one line, s["contacts"]["email"]. But contacts is optional, and inside it email is optional again. A path of two steps has two ways to fail, and the file you test on is never the file that arrives next month.

يسأل فريق التواصل سؤالًا واحدًا: كم مدرسة نستطيع مراسلتها بالبريد؟ الكود البديهي سطر واحد: s["contacts"]["email"]. لكن contacts اختياري، وداخله email اختياري مرة أخرى. فللمسار ذي الخطوتين طريقان للفشل، والملف الذي تختبر عليه ليس هو الملف الذي سيصل الشهر القادم.

First, count which keys existأولًا: عُدَّ المفاتيح الموجودة

Before writing any access code, take a census: how many records carry each key? It is the cheapest schema check there is.

قبل كتابة أي كود وصول، أجرِ تعدادًا: كم سجلًّا يحمل كل مفتاح؟ إنه أرخص فحص للبنية.

import json


def dig(data, *path, default=None):
    """Follow keys (and list positions) through nested data; never raise."""
    current = data
    for step in path:
        if isinstance(current, dict) and step in current:
            current = current[step]
        elif isinstance(current, list) and isinstance(step, int) and -len(current) <= step < len(current):
            current = current[step]
        else:
            return default
    return current

AI lensمنظور الذكاء الاصطناعي

A default is a decision about your data. Had a school lacked its enrolment object and you wrote .get("enrolment", {}).get("boys", 0) "to be safe", that school would enter the table as a school with zero boys: the mean enrolment drops and no error is raised. A missing value left as missing (None, later NaN) can be imputed on purpose or even used as a feature (has_email); a made-up zero cannot be told apart from a real one. The same trap sits in code that reads the arguments of a model's tool call: args.get("amount", 0) turns "the model forgot the amount" into "the amount is zero".

القيمة الافتراضية قرار بشأن بياناتك. لو افتقدت مدرسة كائن enrolment وكتبتَ .get("enrolment", {}).get("boys", 0) «للاحتياط»، لدخلت الجدول مدرسةً بلا بنين: ينخفض متوسط الطلبة ولا يُرفع أي خطأ. أما القيمة الناقصة التي تُترك ناقصة (None ثم NaN) فيمكن تعويضها عن قصد، بل استعمالها خاصية (has_email)؛ والصفر المختلَق لا يمكن تمييزه عن الصفر الحقيقي. وهذا الفخ نفسه في الكود الذي يقرأ وسائط استدعاء أداة من نموذج: args.get("amount", 0) تحوّل «نسي النموذج المبلغ» إلى «المبلغ صفر».

dig() trades loudness for convenience: it never tells you that the structure changed. For a one-off look at a file, a plain [] that crashes is the better tool, because the crash is the information. Use dig only where "absent" is a legitimate, expected state, and pair it with a count.

Flattening in eight lines: a function that calls itselfالتسطيح في ثمانية أسطر: دالة تستدعي نفسها

A record is a dictionary whose values may be dictionaries, whose values may be dictionaries… so the natural tool is recursion: a function that handles the plain values itself and calls itself on every inner dictionary, with a longer prefix. The dotted names are the prefix trail. This is, in essence, what pandas does for you:

السجلّ قاموس قد تكون بعض قيمه قواميس، وقد تكون قيم هذه قواميس أيضًا… فالأداة الطبيعية هي الاستدعاء الذاتي (recursion): دالة تعالج القيم العادية بنفسها وتستدعي نفسها على كل قاموس داخلي ببادئة أطول. والأسماء المنقّطة هي أثر البادئات. وهذا في جوهره ما تفعله pandas عنك:

import json
import pandas as pd


def flatten(d, prefix=""):
    flat = {}
    for key, value in d.items():
        name = prefix + key
        if isinstance(value, dict):
            flat.update(flatten(value, name + "."))      # recurse into the inner object
        else:
            flat[name] = value
    return flat


with open("downloads/t1/schools.json", encoding="utf-8") as f:
    schools = json.load(f)["results"]

mine = pd.DataFrame([flatten(s) for s in schools])
theirs = pd.json_normalize(schools)
print(mine.shape, theirs.shape)
print(mine[theirs.columns].equals(theirs))
(13, 12) (13, 12) True

Our eight-line flatten and pd.json_normalize agree on all 13 schools, down to the cell. Step through one school and watch the call stack: each inner object pushes a frame, its leaves are copied under dotted names, and the frame pops when the object is finished.

Concept 4 — What an API is: a request and a responseالمفهوم 4 — ما الواجهة البرمجية: طلب واستجابة

The problemالمشكلة

Every file so far was handed to you. But the registry changes: schools reopen, enrolments are corrected. A downloaded file is a photograph; by Thursday it is Monday's photograph and nothing inside says so. Re-downloading by hand every morning is exactly the kind of manual step that gets forgotten. The registry's owner offers a door instead: an address your program can ask for the current data. That door is an API.

كل ملف حتى الآن سُلِّم إليك. لكن السجلّ يتغيّر: مدارس تعيد الفتح وأعداد طلبة تُصحَّح. والملف المنزَّل صورة فوتوغرافية؛ وبحلول الخميس يصير صورة الاثنين ولا شيء بداخله يقول ذلك. وإعادة التنزيل يدويًّا كل صباح هي الخطوة اليدوية التي تُنسى. صاحب السجلّ يعرض بدلًا من ذلك بابًا: عنوانًا يستطيع برنامجك أن يطلب منه البيانات الحالية. هذا الباب هو الواجهة البرمجية (API).

An API (application programming interface) is a door that one system opens for other programs, with fixed rules for asking and a fixed shape for answering. A web API runs over HTTP, and every use of it is a conversation of exactly two messages.

الواجهة البرمجية (API) بابٌ يفتحه نظام للبرامج الأخرى، بقواعد ثابتة للسؤال وشكل ثابت للجواب. وتعمل الواجهة على الويب فوق HTTP، وكل استعمال لها حوار من رسالتين بالضبط.

# fake_api.py  -  a classroom stand-in for requests.get that serves the fixture files
import json
from pathlib import Path
from urllib.parse import urlparse, parse_qs

PAGES = Path("downloads/t1")            # where schools_api_page1..3.json live


class HTTPError(Exception):             # plays the part of requests.HTTPError
    pass


class FakeResponse:
    def __init__(self, status_code, body, headers=None):
        self.status_code = status_code
        self._body = body
        self.headers = headers or {}

    def json(self):
        return self._body

    def raise_for_status(self):
        if self.status_code >= 400:
            raise HTTPError(f"{self.status_code} error")


def make_fake_get(script=None, api_key=None):
    """script = {page: [outcome, ...]}: each outcome (429, 500, 503 or "timeout")
    is served once, in order, before the real page. api_key demands a Bearer token."""
    script = {page: list(queue) for page, queue in (script or {}).items()}
    log = []                            # every page number that was asked for

    def fake_get(url, params=None, headers=None, timeout=None):
        parts = urlparse(url)
        query = {k: v[0] for k, v in parse_qs(parts.query).items()}
        query.update(params or {})
        page = int(query.get("page", 1))
        log.append(page)
        if parts.path != "/schools":
            return FakeResponse(404, {"error": "not found"})
        if api_key and (headers or {}).get("Authorization") != f"Bearer {api_key}":
            return FakeResponse(401, {"error": "missing or wrong API key"})
        queue = script.get(page, [])
        if queue:
            outcome = queue.pop(0)
            if outcome == "timeout":
                raise TimeoutError("no reply within the timeout")
            if outcome == 429:
                return FakeResponse(429, {"error": "slow down"}, {"Retry-After": "2"})
            return FakeResponse(outcome, {"error": "server trouble"})
        with open(PAGES / f"schools_api_page{page}.json", encoding="utf-8") as f:
            return FakeResponse(200, json.load(f))

    fake_get.log = log
    return fake_get

Concept 6 — Rate limits, back-off and timeoutsالمفهوم 6 — حدود المعدّل والتباطؤ والمهلات الزمنية

The problemالمشكلة

The loop of Concept 5 asks as fast as the network allows. Servers protect themselves with a rate limit: a cap on how many requests one client may make in a time window. Go over it and the reply is 429 Too Many Requests, usually with a Retry-After header that says how many seconds to wait. Servers also fail (5xx) and sometimes do not answer at all. A script that fetches data needs a policy for each of these, decided in advance, not an improvised reaction at 2 a.m.

حلقة المفهوم 5 تسأل بأسرع ما تسمح به الشبكة. والخوادم تحمي نفسها بـحدّ المعدّل (Rate limit): سقف لعدد الطلبات التي يحق لعميل واحد إرسالها في نافذة زمنية. فإن تجاوزته كان الردّ 429 Too Many Requests وغالبًا معه ترويسة Retry-After تقول كم ثانية تنتظر. والخوادم تفشل أيضًا (5xx) وأحيانًا لا تجيب أصلًا. والسكربت الذي يجلب البيانات يحتاج إلى سياسة لكل حالة، تُقرَّر مسبقًا، لا ردّ فعل مرتجل في الثانية فجرًا.

Three words. Retry: ask again. Back-off: wait longer after each failure (2 s, then 4 s, then 8 s…) so a struggling server gets room to recover instead of a stampede. Timeout: the longest you will wait for a reply before treating the attempt as failed. The conversation looks like this:

ثلاث كلمات. إعادة المحاولة (Retry): اسأل ثانية. التباطؤ (Back-off): انتظر مدة أطول بعد كل فشل (ثانيتان ثم 4 ثم 8…) ليجد الخادم المتعثر فسحة للتعافي بدل أن تندفع عليه. المهلة (Timeout): أطول مدة تنتظر فيها ردًّا قبل أن تعدّ المحاولة فاشلة. وهكذا يبدو الحوار:

From "ask again" to a retry policyمن «اسأل ثانية» إلى سياسة إعادة محاولة

We build one function, get_with_retry(get, url), that fetches one address robustly. Its drivers fetch page 2 while the server misbehaves in scripted ways. The sleep argument lets the demo record the waits instead of really waiting (real code passes time.sleep, the default).

نبني دالة واحدة، get_with_retry(get, url)، تجلب عنوانًا واحدًا بمتانة. وتجلب برامج التشغيل فيها الصفحة 2 بينما يسيء الخادم التصرف بطرائق مبرمجة. ويتيح الوسيط sleep أن يسجّل العرض فترات الانتظار بدل أن ينتظر فعلًا (والكود الحقيقي يمرّر time.sleep وهو الافتراضي).

from fake_api import make_fake_get

URL = "https://api.example.org/schools?page=2"


def get_with_retry(get, url):
    while True:
        resp = get(url)
        if resp.status_code != 429:
            return resp                        # otherwise: ask again, immediately


get = make_fake_get(script={2: [429, 429, 429, 429]})
resp = get_with_retry(get, URL)
print(resp.status_code, "after", len(get.log), "calls and 0 seconds of waiting")

What it does: on a 429, loop and ask again at once. It "works": the fifth call succeeds. What goes wrong: five calls in no time at all, to a server that just said "slow down". A real limiter keeps refusing during its window, so every impatient retry is another refusal and, on some services, a longer penalty. The loop is also unbounded: a server that stays busy keeps this script spinning forever. And it ignores the Retry-After: 2 header the server took the trouble to send.

ماذا تفعل: عند 429 تدور وتسأل فورًا. و«تنجح»: المحاولة الخامسة تنجح. ما الذي يخطئ: خمسة طلبات في لحظة لخادم قال للتو «خفّف». والمحدِّد الحقيقي يواصل الرفض طوال نافذته، فكل إعادة متعجلة رفض آخر، وفي بعض الخدمات عقوبة أطول. والحلقة أيضًا بلا حدّ: خادم يبقى مشغولًا يُبقي هذا السكربت يدور إلى الأبد. وتتجاهل ترويسة Retry-After: 2 التي تكلّف الخادم عناء إرسالها.

import time
from fake_api import make_fake_get

URL = "https://api.example.org/schools?page=2"
RETRYABLE = {429, 500, 502, 503, 504}


def get_with_retry(get, url, params=None, headers=None, max_tries=4, timeout=10, sleep=time.sleep):
    for attempt in range(1, max_tries + 1):
        try:
            resp = get(url, params=params, headers=headers, timeout=timeout)
        except TimeoutError:
            resp = None                                    # a timeout is worth another try
        if resp is not None and resp.status_code not in RETRYABLE:
            return resp                                    # success, or an error a retry cannot fix
        wait = float(2 ** attempt)                         # back-off: 2, 4, 8 ... seconds
        if resp is not None and "Retry-After" in resp.headers:
            wait = float(resp.headers["Retry-After"])      # the server's instruction beats our guess
        if attempt < max_tries:
            sleep(wait)
    raise RuntimeError(f"gave up on {url} after {max_tries} tries")

get = make_fake_get(script={2: [429, "timeout", 500]})
resp = get_with_retry(get, URL, sleep=waits.append)

503 is about the server's load, so time can cure it. 404, 401 and 400 are about your request, which is unchanged by waiting: retrying only wastes time and calls, and hides the real error behind four slow attempts. That is why the retry set holds 429 and the 5xx family, nothing else.
الرمز 503 يتعلق بـ حِمل الخادم، فالزمن يعالجه. أما 404 و401 و400 فتتعلق بـ طلبك الذي لا يغيّره الانتظار: إعادة المحاولة تهدر الوقت والطلبات فقط وتخفي الخطأ الحقيقي خلف أربع محاولات بطيئة. ولهذا لا تضم مجموعة الإعادة إلا الرمز 429 وعائلة 5xx.

AI lensمنظور الذكاء الاصطناعي

On a model API a retry loop is also a cost loop. These services meter by request and by token, and 429 is routine at volume. An unbounded retry on a paid call can multiply the bill, and a POST that timed out may already have been processed (and billed) on the server — unlike a GET, repeating it is not free of side effects. Use the bounded policy of Version 3, log every retry so you can see the real failure rate, and add the pause between calls when you label thousands of documents. In the worst case Version 3 spends 2 + 4 + 8 = 14 s of waiting on one page and then stops; that ceiling is the point.

في واجهة نموذج تكون حلقة إعادة المحاولة أيضًا حلقة تكلفة. هذه الخدمات تحسب بالطلب وبالرمز (token)، والرمز 429 معتاد عند الأحجام الكبيرة. وإعادة محاولة بلا حدّ على استدعاء مدفوع قد تضاعف الفاتورة، والـ POST التي انتهت مهلتها ربما عولجت (وحوسبت) على الخادم أصلًا — وبخلاف GET لا يخلو تكرارها من آثار جانبية. استعمل السياسة المحدودة في النسخة 3، وسجّل كل إعادة لترى معدّل الفشل الحقيقي، وأضف التوقف بين الاستدعاءات حين تُرمّز آلاف الوثائق. وفي أسوأ الأحوال تنفق النسخة 3 على الصفحة الواحدة 2 + 4 + 8 = 14 ثانية انتظار ثم تتوقف؛ وهذا السقف هو المقصود.

Honest accountingحساب صادق

Retries hide a flaky server: if every fifth page needs a second try you want to know, so count them. Back-off here is deterministic; real systems add random "jitter" so that many clients do not all retry at the same instant. Retrying is safe for a GET, not automatically for a POST. And for a three-page fetch you run once a month, a simpler script that fails loudly and is re-run by hand may be the better engineering. Production code often uses a tested library (urllib3.util.Retry with a requests session, or tenacity) rather than a hand-made loop — but now you know what those libraries do.

إعادة المحاولة تخفي خادمًا متقلبًا: إن احتاجت كل صفحة خامسة إلى محاولة ثانية فأنت تريد أن تعرف، فعُدَّها. والتباطؤ هنا حتمي؛ أما الأنظمة الحقيقية فتضيف «تشويشًا» عشوائيًّا (jitter) كي لا يعيد عملاء كثيرون المحاولة في اللحظة نفسها. وإعادة المحاولة آمنة مع GET لا مع POST تلقائيًّا. ولجلب من ثلاث صفحات تشغّله مرة في الشهر قد يكون السكربت الأبسط الذي يفشل بصوت عالٍ ويُعاد تشغيله يدويًّا هو الهندسة الأفضل. وغالبًا يستعمل الكود الإنتاجي مكتبة مختبَرة (urllib3.util.Retry مع جلسة requests، أو tenacity) بدل حلقة مصنوعة يدويًّا — لكنك الآن تعرف ماذا تفعل تلك المكتبات.

Concept 7 — fetch_all(), secrets, and model JSONالمفهوم 7 — fetch_all() والأسرار وJSON النماذج

The problemالمشكلة

You now own the ingredients: a status check, a page loop, a retry policy, a timeout. Scattered through a notebook they get copied wrong: one cell checks the status, another forgets, a third pastes the key into the code. What an analysis needs is one function with a contract: it returns a complete, checked table, or it raises. It never returns half of the schools and lets you find out in a chart.

تملك الآن المكوّنات: فحص الحالة وحلقة الصفحات وسياسة إعادة المحاولة والمهلة. وحين تتناثر في دفتر تُنسخ خطأً: خلية تفحص الحالة وأخرى تنساها وثالثة تلصق المفتاح في الكود. ما يحتاجه التحليل هو دالة واحدة لها عقد: تعيد جدولًا كاملًا مفحوصًا أو ترفع خطأً. ولا تعيد أبدًا نصف المدارس وتدعك تكتشف ذلك في رسم بياني.

One function, one contractدالة واحدة وعقد واحد

Keep get_with_retry from Concept 6 in the same file. fetch_all follows next, hands every request to get_with_retry, turns any non-retryable error into an exception with raise_for_status(), collects the records, flattens them, and checks the result against what the server announced.

أبقِ get_with_retry من المفهوم 6 في الملف نفسه. تتبع fetch_all الحقل next، وتسلّم كل طلب إلى get_with_retry، وتحوّل أي خطأ غير قابل للإعادة إلى استثناء بـ raise_for_status()، وتجمع السجلات وتسطّحها، وتقارن النتيجة بما أعلنه الخادم.

import time
import pandas as pd


def fetch_all(get, first_url, headers=None, sleep=time.sleep):
    rows, url, total = [], first_url, None
    while url:
        resp = get_with_retry(get, url, headers=headers, sleep=sleep)
        resp.raise_for_status()                  # a 4xx that retrying cannot fix: stop, loudly
        payload = resp.json()
        rows.extend(payload["results"])
        total, url = payload["total"], payload["next"]
    df = pd.json_normalize(rows, sep="_")
    if len(df) != total or not df["id"].is_unique:
        raise ValueError(f"expected {total} distinct schools, got {len(df)} rows")
    return df

Why does fetch_all call resp.raise_for_status() after get_with_retry has already returned?لماذا تستدعي fetch_all الدالة resp.raise_for_status() بعد أن أعادت get_with_retry ردًّا؟

Division of labour: get_with_retry decides whether to try again; raise_for_status() decides whether what finally arrived is acceptable. Without it a 404 reply would flow on and fail at ["results"] with a KeyError, which is Version 1 of Concept 5 all over again. Parsing is .json()'s job and the timeout is applied inside the call.
تقسيم العمل: تقرّر get_with_retry هل نحاول مجددًا؛ وتقرّر raise_for_status() هل ما وصل أخيرًا مقبول. وبدونها يمرّ ردّ 404 ويفشل عند ["results"] بـ KeyError، وهذه هي النسخة 1 من المفهوم 5 من جديد. أما التحليل فمهمة .json()، وتُطبَّق المهلة داخل الاستدعاء.

Where this stops being the whole truthحيث يتوقف هذا عن أن يكون الحقيقة كلها

The classroom server proves your logic, not the real server's habits. Real services name things differently — the records may sit under data, the total under meta.total_pages, the next page in a Link header — and they add headers, versions and their own error bodies. Read the provider's documentation and adapt the three lines that touch those names; the structure (status, loop, retry, validate) stays.

الخادم الصفّي يثبت منطقك لا عادات الخادم الحقيقي. الخدمات الحقيقية تسمّي الأشياء بطرائق أخرى — قد تقع السجلات تحت data والإجمالي تحت meta.total_pages والصفحة التالية في ترويسة Link — وتضيف ترويسات وإصدارات وأجسام أخطاء خاصة بها. اقرأ توثيق المزوّد وعدّل الأسطر الثلاثة التي تلمس هذه الأسماء؛ أما البنية (الحالة والحلقة وإعادة المحاولة والتحقق) فتبقى.

import json

REQUIRED = {"id": int, "governorate": str, "enrolment_total": int}


def parse_model_json(text):
    """Turn a model's reply into a checked dict, or raise ValueError saying why."""
    start, end = text.find("{"), text.rfind("}")
    if start == -1 or end < start:
        raise ValueError("no JSON object in the reply")
    try:
        data = json.loads(text[start:end + 1])
    except json.JSONDecodeError as err:
        raise ValueError(f"not valid JSON: {err.msg}") from err
    for key, kind in REQUIRED.items():
        if key not in data:
            raise ValueError(f"missing key {key!r}")
        if not isinstance(data[key], kind) or isinstance(data[key], bool):
            raise ValueError(f"{key!r} should be {kind.__name__}, got {type(data[key]).__name__}")
    return data

A pipeline from an API to a model is a chain: fetch_all → DataFrame → features → training. Every link either returns a complete, checked result or raises. The silent alternatives — a truncated fetch, a swallowed JSON error, a None turned into a zero — are what make "the model got worse after the data refresh" impossible to debug, because nothing ever said that the data had changed. In the six replies above, a loop that skips failures would have kept 2 of 6 rows and reported nothing; with your labelled data that is a training set one third the size you believe, and not a random third. Count, compare to what you asked for, and fail loudly.

خط المعالجة من واجهة إلى نموذج سلسلة: fetch_all ← DataFrame ← خصائص ← تدريب. وكل حلقة إما تعيد نتيجة كاملة مفحوصة أو ترفع خطأً. والبدائل الصامتة — جلب مبتور، وخطأ JSON مبلوع، وَNone تحوّل إلى صفر — هي ما يجعل «ساء النموذج بعد تحديث البيانات» مستحيل التصحيح، لأن شيئًا لم يقل يومًا إن البيانات تغيّرت. وفي الردود الستة أعلاه كانت الحلقة التي تتخطى الإخفاقات ستبقي 2 من 6 صفوف ولا تبلّغ بشيء؛ ومع بياناتك الموسومة هذه مجموعة تدريب بثلث الحجم الذي تظنه، وليست ثلثًا عشوائيًّا. عُدّ، وقارن بما طلبتَ، واخفق بصوت عالٍ.

from fake_api import make_fake_get

URL = "https://api.example.org/schools"


def all_ids(get, first_url, max_pages=10):
    ids, url = [], first_url
    for _ in range(max_pages):                       # bounded: a bug cannot loop forever
        resp = get(url)
        resp.raise_for_status()
        payload = resp.json()
        ids.extend(school["id"] for school in payload["results"])
        url = payload["next"]
        if url is None:
            return ids
    raise RuntimeError("more than max_pages pages - is `next` ever None?")

Appendix — the arithmetic behind page counts and back-offملحق — الحساب وراء عدد الصفحات والتباطؤ

Requests per fetch. With total records and per_page records per reply, the number of requests is ceil(total / per_page). The registry: ceil(13 / 5) = 3. As an illustration (not registry data), 10,000 records at 100 per page need 100 requests, at 20 per page 500. Under an assumed limit of 60 requests a minute that is at least 100 s against 500 s, about 8 min 20 s, before any retry.

الطلبات في كل جلب. مع total سجلًّا وper_page سجلًّا في الردّ يكون عدد الطلبات ceil(total / per_page). في السجلّ: ceil(13 / 5) = 3. وللتوضيح فقط (وليس من بيانات السجلّ): 10,000 سجلّ بواقع 100 في الصفحة تحتاج 100 طلب، وبواقع 20 تحتاج 500. وبافتراض حدّ 60 طلبًا في الدقيقة يعني ذلك 100 ثانية على الأقل مقابل 500 ثانية، أي نحو 8 دقائق و20 ثانية، قبل أي إعادة محاولة.

Total back-off. With waits of 2^k seconds after failed attempt k, and no sleep after the last of n attempts, the longest total wait is the geometric sum 2^1 + 2^2 + … + 2^(n−1) = 2^n − 2. For n = 4: 2 + 4 + 8 = 14 seconds per page. A Retry-After from the server replaces the term for that attempt. Doubling the number of tries to 8 does not double the worst case: it raises it to 2^8 − 2 = 254 seconds, which is why max_tries and a cap on the wait belong together.

إجمالي التباطؤ. مع انتظار 2^k ثانية بعد المحاولة الفاشلة رقم k ودون نوم بعد آخر محاولة من n، يكون أطول انتظار إجمالي هو المجموع الهندسي 2^1 + 2^2 + … + 2^(n−1) = 2^n − 2. وعند n = 4: 2 + 4 + 8 = 14 ثانية للصفحة. وترويسة Retry-After من الخادم تحلّ محل الحدّ في تلك المحاولة. ومضاعفة المحاولات إلى 8 لا تضاعف أسوأ الحالات بل ترفعه إلى 2^8 − 2 = 254 ثانية، ولهذا تتلازم max_tries وسقف للانتظار.
