Concept 1 — A notebook is cells, a kernel and a JSON fileالمفهوم 1 — الدفتر خلايا ونواة وملف JSON

The problemالمشكلة

You have run Python as a script: you write a file, run it from top to bottom, it ends, and everything it knew is forgotten. A notebook does not behave like that, and the difference is invisible on the page. Variables stay alive between cells, outputs are saved inside the file, and the order in which you ran things matters more than the order in which they appear. If you picture a notebook as “a script cut into pieces” or as “a Word document with live code”, you will sooner or later quote a number that no code on the page can produce.

شغّلتَ بايثون حتى الآن كسكربت: تكتب ملفًا وتشغّله من أوله إلى آخره ثم ينتهي وينسى كل ما عرفه. الدفتر لا يتصرف هكذا، والفرق غير مرئي على الصفحة. تبقى المتغيّرات حيّة بين الخلايا، وتُحفظ النواتج داخل الملف، ويصير ترتيب تشغيلك للخلايا أهم من ترتيب ظهورها. فإن تخيّلتَ الدفتر «سكربتًا مقطّعًا» أو «مستند Word فيه شيفرة حيّة» فستذكر عاجلًا أو آجلًا رقمًا لا تستطيع أي شيفرة في الصفحة إنتاجه.

Three parts, one pictureثلاثة أجزاء، صورة واحدة

A notebook is a document made of cells. A code cell holds Python that you can run. A Markdown cell holds formatted text — headings, explanations, a list of assumptions — and never runs. A raw cell is passed through untouched by export tools and you will rarely need one. Code cells do not run themselves: when you run one, the page sends its text to the kernel, a separate Python process that Jupyter starts for the notebook. The kernel executes the code, keeps every variable it creates in memory, and sends the output back.

الدفتر (Notebook) مستند يتكوّن من خلايا (Cells). تحمل خلية الشيفرة بايثون يمكنك تشغيله. وتحمل خلية Markdown نصًّا منسّقًا — عناوين وشروحًا وقائمة افتراضات — ولا تُشغَّل أبدًا. أما الخلية الخام (raw) فتمرّ دون تغيير عبر أدوات التصدير وقلّما تحتاج إليها. لا تُشغِّل خلايا الشيفرة نفسها: عندما تشغّل واحدة ترسل الصفحة نصّها إلى النواة (Kernel)، وهي عملية بايثون منفصلة يبدؤها Jupyter للدفتر. تنفّذ النواة الشيفرة وتحتفظ في الذاكرة بكل متغيّر تنشئه وتعيد الناتج.

The third part is the .ipynb file on disk, where Jupyter saves your cells and their outputs. The picture below follows one cell from the keyboard to the file. Read the last row twice: the variables are in the kernel, and the file never contains them.

والجزء الثالث هو ملف ‎.ipynb على القرص، حيث يحفظ Jupyter خلاياك ونواتجها معًا. يتتبّع المخطط أدناه خلية واحدة من لوحة المفاتيح إلى الملف. اقرأ السطر الأخير مرتين: المتغيّرات في النواة، والملف لا يحتويها أبدًا.

Outputs are a photograph; the kernel is the roomالنواتج صورة فوتوغرافية، والنواة هي الغرفة

Today you open the file: the page shows Out[12]: 8062.0 under a cell, so it looks as if the notebook knows the revenue. It does not. In machine learning the stored output is often the headline: a cell prints validation accuracy: 0.91, the notebook is committed, and a month later the code above it has been edited (a different feature set, a new split) while the 0.91 still sits in the file. A reviewer who trusts the photograph reports a model nobody can rebuild. Part of the habit you are learning is to treat a stored metric as a claim that must be re-run.

في تعلّم الآلة كثيرًا ما يكون الناتج المحفوظ هو العنوان الرئيس: تطبع خلية validation accuracy: 0.91، ويُحفظ الدفتر، وبعد شهر تكون الشيفرة التي فوقها قد عُدّلت (مجموعة خصائص مختلفة، تقسيم جديد) بينما ما زال 0.91 في الملف. والمراجع الذي يصدّق الصورة الفوتوغرافية يُبلّغ عن نموذج لا يستطيع أحد إعادة بنائه. وجزء من العادة التي تتعلمها أن تعامل أي مقياس محفوظ على أنه ادّعاء يجب إعادة تشغيله.

Honest accountingحساب أمين

This design buys you something real: you see a result the instant you run a cell, and you can build an analysis in small, inspectable steps. The price is that the file looks finished when it is not. Everything in Concepts 4–8 is the discipline that pays this price.

هذا التصميم يمنحك شيئًا حقيقيًّا: ترى النتيجة لحظة تشغيل الخلية، وتبني التحليل بخطوات صغيرة قابلة للفحص. وثمنه أن الملف يبدو منتهيًا وهو ليس كذلك. وكل ما في المفاهيم 4–8 هو الانضباط الذي يسدّد هذا الثمن.

Concept 2 — The interface: two modes, a few shortcuts, one menuالمفهوم 2 — الواجهة: وضعان وبضعة اختصارات وقائمة واحدة

The problemالمشكلة

A beginner reaches for the mouse for everything — click a cell, click the Run button, click the plus sign — and a notebook session becomes slow. Worse, a beginner who does use the keyboard types a word while the notebook is listening for commands. Press d twice in the wrong place and a cell is gone; press a and a new cell appears instead of a letter. The cause is that the notebook has two keyboards in one.

يمدّ المبتدئ يده إلى الفأرة لكل شيء — ينقر خلية، وينقر زر التشغيل، وينقر علامة الزائد — فتصير جلسة الدفتر بطيئة. والأسوأ أن المبتدئ الذي يستعمل لوحة المفاتيح يكتب كلمة والدفتر يصغي إلى أوامر. اضغط d مرتين في المكان الخطأ فتختفي خلية؛ واضغط a فتظهر خلية جديدة بدل حرف. والسبب أن الدفتر فيه لوحتا مفاتيح في لوحة واحدة.

Command mode and edit modeوضع الأوامر ووضع التحرير

In edit mode a cell has a text cursor and your keys type characters, as in any editor. In command mode the cell itself is selected, there is no cursor, and single letter keys are commands that act on cells. Press Esc to go from edit to command mode and Enter to go back. Clicking inside a cell enters edit mode; clicking in the margin selects the cell in command mode. To see which mode you are in, look at the colour bar on the left of the active cell, and in JupyterLab at the status bar at the bottom of the window, which reads Mode: Command or Mode: Edit. The classic Notebook colours the border blue for command and green for edit; menu names and colours vary slightly by version.

في وضع التحرير (Edit mode) يظهر مؤشر نصّي داخل الخلية وتكتب مفاتيحك حروفًا كما في أي محرّر. وفي وضع الأوامر (Command mode) تكون الخلية نفسها محدَّدة، ولا يوجد مؤشر، وتصبح مفاتيح الحروف المفردة أوامر تعمل على الخلايا. اضغط Esc للانتقال من التحرير إلى الأوامر وEnter للعودة. النقر داخل الخلية يدخل وضع التحرير، والنقر في الهامش يحدّد الخلية في وضع الأوامر. لمعرفة وضعك انظر إلى الشريط الملوّن على يسار الخلية النشطة، وفي JupyterLab إلى شريط الحالة أسفل النافذة الذي يقرأ Mode: Command أو Mode: Edit. ويلوّن الدفتر الكلاسيكي الحدّ بالأزرق للأوامر وبالأخضر للتحرير؛ وتختلف أسماء القوائم والألوان قليلًا باختلاف الإصدار.

The Kernel menu: Interrupt, Restart, Restart & Run Allقائمة Kernel: المقاطعة وإعادة التشغيل وإعادة التشغيل مع تنفيذ الكل

Because the kernel is a separate process, you can control it separately from the page. Three actions cover nearly everything. Interrupt stops the cell that is running — an infinite loop, a read of a huge file — but the kernel and all its variables survive. Restart kills the process and starts a fresh one: every variable is gone, and every output stays on the page. Restart & Run All restarts the kernel and then runs every code cell once, from top to bottom, in page order. That last one is the only honest answer to the question “does this notebook work?”, and Concept 4 shows why. In JupyterLab the items are under Kernel (Interrupt Kernel, Restart Kernel…, Restart Kernel and Run All Cells…); VS Code has Restart and Run All buttons in the notebook toolbar; Google Colab calls it Runtime → Restart session and run all. Names vary slightly by version.

Three runs of the same page, three answers. Cell 4 changes the table in place (*=), so each extra run discounts values that were already discounted: 0.9, then 0.81, then 0.729. Restart & Run All is the disciplineRestart & Run All هو الانضباط

The honest test of a notebook is whether it gives the same answer when it is run once, from a fresh kernel, top to bottom — that is, whether it is reproducible: the same steps on the same data give the same answer on another day or another machine. Kernel → Restart Kernel and Run All Cells performs exactly that test. Do it before you quote a number, before you share the file, and before you go to lunch. You can also run it without a browser; jupyter nbconvert --execute (Concept 7) is Restart & Run All from the command line, and a notebook whose cell fails stops with the error. A rule of thumb for safe cellsقاعدة عملية لخلايا آمنة

A cell is safe to re-run if running it twice gives the same state as running it once. orders = orders.drop_duplicates() is safe; orders = orders.iloc[1:], total += x, df.drop(columns=["a"], inplace=True) and *= on a column from an earlier cell are not. Prefer new names to rebinding old ones, and keep the one-time loading of data in one cell you rarely touch.

The kernel and the page are separate: deleting a cell edits the page, not the kernel’s memory. Nothing in Jupyter re-creates deleted code or fills in missing names; a fresh kernel raises NameError. This is why “it works on my machine” is the typical symptom of hidden state.

AI lensمنظور الذكاء الاصطناعي

Hidden state is how test data leaks into training without a single error. Cell 5 runs train_test_split(X, y, test_size=0.2) with no seed; cell 6 fits a model on X_train. You re-run cell 5 (a new random split), skip cell 6, and evaluate in cell 8 on the new X_test — but the model in memory was fitted on the old X_train, about 80% of which now overlaps the new test set. The accuracy rises and nothing complains. The remedies are the ones in this concept: fix the seed in the split (random_state=42), never evaluate after a partial re-run, and report only numbers produced by a Restart & Run All.

الحالة الخفية هي الطريقة التي تتسرّب بها بيانات الاختبار إلى التدريب دون خطأ واحد. تشغّل الخلية 5 الدالة train_test_split(X, y, test_size=0.2) بلا بذرة؛ وتدرّب الخلية 6 نموذجًا على X_train. فتعيد تشغيل الخلية 5 (تقسيم عشوائي جديد)، وتتخطى الخلية 6، وتقيّم في الخلية 8 على X_test الجديد — لكن النموذج الموجود في الذاكرة دُرّب على X_train القديم الذي يتقاطع نحو 80% منه الآن مع مجموعة الاختبار الجديدة. فترتفع الدقة ولا يشتكي شيء. والعلاج هو ما في هذا المفهوم: ثبّت البذرة في التقسيم (random_state=42)، ولا تقيّم أبدًا بعد إعادة تشغيل جزئية، ولا تذكر إلا أرقامًا أنتجها Restart & Run All.

Honest accountingحساب أمين

Restart & Run All does not prove the answer is right; it proves the page explains the number. It cannot catch an unseeded random step, a data file that changed since yesterday, or a web request that returns something new. It also gets expensive: a notebook that takes forty minutes to run is no longer something you test casually, and that is one signal that it belongs in a script (Concept 8). Some tools — marimo is one — re-run dependent cells automatically to remove this class of bug; Jupyter does not.

لا يثبت Restart & Run All أن الجواب صحيح؛ بل يثبت أن الصفحة تشرح الرقم. ولا يستطيع أن يلتقط خطوة عشوائية بلا بذرة، ولا ملف بيانات تغيّر منذ أمس، ولا طلب ويب يعيد شيئًا جديدًا. وهو يصبح مكلفًا أيضًا: فالدفتر الذي يستغرق تشغيله أربعين دقيقة لم يعد شيئًا تختبره بخفة، وهذه إحدى إشارات أن مكانه سكربت (المفهوم 8). وبعض الأدوات — منها marimo — تعيد تشغيل الخلايا المعتمدة تلقائيًّا لتزيل هذا الصنف من الأخطاء؛ أما Jupyter فلا يفعل.

Two things silently decide whether a model run can be repeated: the random seed and the library versions. Put both in the header cell: rng = np.random.default_rng(42) for NumPy, random_state=42 in scikit-learn calls, and a framework seed such as torch.manual_seed(42), plus the printed version line you saw above. The same dirty rows that bend a revenue total damage a model in specific ways. If item is a label to predict, Latte and latte become two classes and the model is punished for the correct answer. If the 16 exact duplicates land on both sides of a train/test split, the test set contains rows the model has already seen and the accuracy is inflated, a form of leakage. A price of 120.0 for a 12.0 item is a feature outlier that a distance-based model will treat as real. In every case the code ran without an error.

import pandas as pd
import matplotlib.pyplot as plt

def load_orders(path):
    """Read the raw file, fix item names, drop the rows we agreed not to count."""
    orders = pd.read_csv(path)
    orders["item"] = orders["item"].str.strip().str.title()
    orders["line_total"] = orders["qty"] * orders["unit_price"]
    orders = orders.drop_duplicates()
    return orders[(orders["qty"] > 0) & (orders["unit_price"] < 50)]


def revenue_by_item(orders):
    """Revenue per item, biggest first."""
    return orders.groupby("item")["line_total"].sum().sort_values(ascending=False)

The problemالمشكلة

"""Print the top items by revenue for one cafeteria orders file."""
import sys
from pathlib import Path

import pandas as pd

DEFAULT = Path("data/raw/cafeteria_orders.csv")


def load_orders(path):
    orders = pd.read_csv(path)
    orders["item"] = orders["item"].str.strip().str.title()
    orders["line_total"] = orders["qty"] * orders["unit_price"]
    orders = orders.drop_duplicates()
    return orders[(orders["qty"] > 0) & (orders["unit_price"] < 50)]


def revenue_by_item(orders):
    return orders.groupby("item")["line_total"].sum().sort_values(ascending=False)


def main(path):
    revenue = revenue_by_item(load_orders(path))
    print("Top 3 items by revenue")
    for rank, (item, total) in enumerate(revenue.head(3).items(), start=1):
        print(f"{rank}. {item:<18}{total:>10,.2f}")


if __name__ == "__main__":
    main(Path(sys.argv[1]) if len(sys.argv) > 1 else DEFAULT)

Honest accountingحساب أمين

Do not graduate too early. A script has no inline plots and no table to poke at, so the exploring gets slower; and a module that only you understand is not better than a tidy notebook. Converting back and forth loses outputs and Markdown unless you use a pairing tool such as jupytext. Some teams run notebooks themselves on a schedule (nbconvert --execute, or tools such as papermill); that works for small jobs, but you keep the hidden-state risk and gain no tests. A one-off analysis for one reader should stay a notebook.

لا تتخرّج مبكرًا. فالسكربت بلا رسوم مضمَّنة ولا جدول تنقّب فيه، فيبطؤ الاستكشاف؛ والوحدة التي لا يفهمها غيرك ليست أفضل من دفتر مرتب. والتحويل ذهابًا وإيابًا يُفقد النواتج وMarkdown ما لم تستعمل أداة اقتران مثل jupytext. وبعض الفرق تشغّل الدفاتر نفسها بجدول زمني (nbconvert --execute أو أدوات مثل papermill)؛ وينجح ذلك في المهام الصغيرة، لكنك تحتفظ بخطر الحالة الخفية ولا تكسب اختبارات. أما التحليل لمرة واحدة لقارئ واحد فيبقى دفترًا.

"""Print the busiest hour of the day, counting distinct orders."""
import sys
from pathlib import Path

import pandas as pd

from cafeteria_report import load_orders


def busiest_hour(orders):
    hours = pd.to_datetime(orders["order_time"]).dt.hour
    per_hour = orders.groupby(hours)["order_id"].nunique()
    return int(per_hour.idxmax()), int(per_hour.max())


def main(path):
    hour, count = busiest_hour(load_orders(path))
    print(f"Busiest hour: {hour}:00 with {count} orders")


if __name__ == "__main__":
    main(Path(sys.argv[1]) if len(sys.argv) > 1 else Path("data/raw/cafeteria_orders.csv"))

Appendix A — A 20-line notebook checkerالملحق أ — أداة فحص دفاتر في 20 سطرًا

Concept 1 said a notebook is just JSON. That makes hidden-state symptoms easy to look for automatically. This checker reads a saved notebook and flags code cells that were never run, or whose counters are not exactly 1, 2, 3… in page order (which is what a Restart & Run All produces). It cannot see the kernel; it reads the counters the file kept. Save it as nblint.py:

قال المفهوم 1 إن الدفتر مجرد JSON. وهذا يسهّل البحث عن أعراض الحالة الخفية آليًّا. تقرأ هذه الأداة دفترًا محفوظًا وتشير إلى خلايا الشيفرة التي لم تُشغَّل قط أو التي ليست عدّاداتها بالضبط 1 و2 و3… بترتيب الصفحة (وهذا ما ينتجه Restart & Run All). وهي لا ترى النواة؛ بل تقرأ العدّادات التي احتفظ بها الملف. احفظها باسم nblint.py:

import json
import sys


def lint(path):
    """Return a list of problems that betray hidden state in a saved notebook."""
    with open(path, encoding="utf-8") as f:
        nb = json.load(f)
    counters = [c["execution_count"] for c in nb["cells"] if c["cell_type"] == "code"]
    problems = []
    if None in counters:
        problems.append("some code cells were never run")
    elif counters != list(range(1, len(counters) + 1)):
        problems.append(f"counters {counters} are not 1..{len(counters)}: "
                        "cells ran out of order, twice, or the kernel was not restarted")
    for c in nb["cells"]:
        if c["cell_type"] == "code" and any(o["output_type"] == "error" for o in c["outputs"]):
            problems.append("a cell saved with an error output")
    return problems


if __name__ == "__main__":
    for path in sys.argv[1:]:
        found = lint(path)
        print(path, "->", "OK" if not found else "; ".join(found))

An OK proves very little (a notebook can be run once in a stale kernel), but a failure is a reliable reason to run Restart & Run All before sharing. You could run the same check in a pre-commit hook or a continuous-integration job (an automatic check that runs whenever code is pushed), together with nbconvert --execute.
